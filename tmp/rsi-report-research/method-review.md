# RSI 报告方法评审备忘

本备忘只审查结论的边界与后续实验设计；没有运行 self-evolve、修改源码或重算原始评分。直接阅读范围为 `.agent/progress.md` 前 45 行，以及两个任务导出的用户与助手外显文本。第一份导出只有最近 8 轮，`hasMore=true`；其中未出现的早期过程不能据此判定不存在。主任务补充核查的早期门槛变化、最终 measurement 与 held-out 字段列为下文的限制条件。

## 1. 最强结论仍然是一次有条件的工程验收

可以写：在修复后的 v19 框架及其当时生效的验收规则下，一份由 self-evolve 生成的 `agent-browser` 候选完成了配对回放、正式 gate 检查、独立回归及隔离包验证，原命令返回 `Status: succeeded`。记录给出的主配对评分为 86.6667 → 89.4667，差值 +2.8，区间为 [0.16950, 5.43050]；延迟降低 9.3292%，回放 token 增加 1.4271%。这些数值描述该次测量，不能顺推所有任务都有改善。

需要同时说清楚三处边界：

- 交付模式是 `verified_only`，源技能没有替换，`published=false`。隔离包可加载与正式投入使用是两件事。
- 主任务核查到 measurement 视图仍有 `shadow`、`effect_direction=unmeasured`、`effect_estimate=null`、`primary_effect_unavailable`、`promotion_eligible=false`。在确认这些字段的契约和关联对象前，报告应并列陈述“正式验收通过”与“该测量视图未给出可晋升效果”，不能把 gate 的配对分数代替 measurement 字段，也不能擅自把这些字段解释为普通展示错误。
- 最终 held-out 按 baseline-relative 规则通过，仍有 `evidence_incomplete=true` / `support_incomplete` 记录。通过的含义是满足当时的相对规则，不是每个答案都无证据缺口，更不是零幻觉。

不能写：已证明通用的递归自我改进、已证明连续多代能力上升、改进速度会自我加快、对开放分布稳定泛化、无需外部工程介入。两个任务展示的更准确对象，是候选自动生成与评估循环，在外部 Coding Agent 反复修复框架后完成一次目标验收。后期接连出现候选质量失败，也表明“流程能运行”与“候选会变好”须分别判断。

## 2. “冻结评估”必须标明冻结的时间和对象

至少有三个不同层次，不能共用一句“评估标准始终没变”：

1. **单次测量内冻结。** 同一候选、数据、judge/backend、执行计划和配对口径保持一致，使本轮对照可解释。运行中隔离开发框架修复、等完整结果落盘再整合，是此层面的好做法。
2. **相邻实验间可追踪变更。** 框架修复会改变反馈可见性、候选搜索方向、预算使用、统计复评流程，甚至可进入权威评估的候选集合。原始文件哈希没变只能证明没有篡改那些文件，不能证明测量制度或后续搜索分布没变。
3. **整段研发期外部评估冻结。** 本次不满足“整段研发只在固定且不可接触的评估器上改候选”这一强条件。主任务核查到早期 held-out 从候选单臂零缺陷转为 paired baseline-relative，并调整 screening/authoritative tool envelope 为 12/48。后期特定修复保留当时阈值，可以如实写；它不能追溯为全过程规则不变。

建议把过程分成“验收规则与框架开发期”以及“最终版本上的确认运行”。前者的价值是暴露并修正系统缺陷，后者的价值是记录该版本实际达成的结果。不能将早期失败率与后期成功率直接作纯候选能力的前后因果比较，因为框架、搜索器和运行条件也在变。

一个具体例子：历史加载修复在固定 12 条记录额度下恢复后续已通过检查点，实际输入审计证明了反馈选择变化；v19 第二轮成功与这一机制相符，但不足以证明“就是这个修复造成 +2.8 分”。若要作该因果结论，需要等预算、等候选起点、等评估器的对照运行。

## 3. 把候选改进与改进器被修复分开记账

本案可分两条链：

- **内层候选链：** 模型改写技能/支持文件，继承候选，接收真实失败反馈，接受筛选和完整评估。例如从回答中删除或限定缺乏来源支持的主张。
- **外层工程链：** Coding Agent 修复候选生成/物化、预算、续跑去重、错误归因、反馈压缩、历史排序、tie-break 和验收脚本，并用测试、真实输入 A/B、独立审查确认。它改变的是自进化系统能否正确工作。

这两条链共同带来了结果，但只有内层候选变化能算作这次 self-evolve 自动生成的候选改动。外层 Agent 的工程成果不能直接记成“系统自主提升了自己的改进算法”。报告可以称其为“面向 RSI 的工程探索”或“外部工程协助下的自改进闭环”，并说明 RSI 在此作为研究方向而非已被证明的系统能力。

建议每个案例明确填写四项：失败的责任对象、外部 Agent 改了什么、候选自己改了什么、用哪份原生证据验证。对推断使用“与……相符”“提示可能”，对真实输入 A/B 才使用“该字段确实缺失/选择确实改变”。

## 4. 有界 tie-break 没有解决整段搜索的选择偏差

记录中的 tie-break 有实质约束：同一候选/数据/backend/计划，最多增加一次测量，合并全部相容样本，不挑高分轮，拒绝异常或身份不一致的证据，并计入预算。这比无限重测、只取最好的一轮更可审计。负点估计不进入相应主选择 tie-break 的案例也说明拒绝路径在生效。

但仍要分清两类重复：

- **候选固定后的有界补充测量：** 处理本候选统计不确定性，是一个局部决策程序。有限次数、合并样本不自动证明整套顺序检验已校准；未核查完整统计契约时，不应宣称其已消除所有可选停止影响。
- **持续修改候选/框架并反复启动 campaign，直到出现成功：** 成功候选从许多尝试中被选出。即使每轮都诚实记录，也不能只用胜出轮的区间代表整个开发策略的真实收益或长期成功率。失败运行、消耗、被中止候选以及规则版本都应进入分母。

独立回归仍然能限制某个候选在额外任务上的退化，但当其具体问题被送回生成器，后来候选已经间接看到测试反馈；它对单轮评估可以独立，对整段研发则不再是未触碰的最终外部检验。最终论证需要另设此前没有反馈给生成器的任务集。

## 5. 建议后续实验：先限定问题，再写通过判据

以下均为建议，未在本次任务中执行。样本量、随机种子、总预算及停止规则应在运行前登记；小规模先导可以估计方差，不应被当作正式确认。

| 实验 | 固定项与操作 | 事先判据 | 能回答什么 |
| --- | --- | --- | --- |
| 冻结最终包，在新任务上复验 | 固定 v19 源码、原始基线包、最终候选、judge 及资源预算；用此前没有进入任何修复反馈的新任务作配对评估；保存所有结果 | 主效应达到预先登记的提升标准，同时证据质量、成本与回归满足明确写出的规则；measurement/promotion 字段与正式结论一致或有经契约确认的解释 | 最终包能否在未参与研发反馈的任务上复现收益 |
| 候选与框架的交叉对照 | 用可兼容的旧/新框架分别运行基线/最终候选；相同任务与预算，保留失败运行；无法兼容的组合单列为不可测 | 分别报告候选效应、框架效应及两者交互；只有同框架下的基线/候选对照才归因为候选收益 | 收益来自技能变化、框架修复，还是两者共同作用 |
| 历史反馈修复消融 | 固定一个存在祖先覆盖问题的历史快照，对照旧排序/加载与修复后的策略；提示预算相同；候选种子和总预算预先固定 | 先验证新策略能保留正确父子关系与已通过检查点、没有证据越权；再比较等预算的最终通过率及成本，而非只比较是否选中预期 ID | 修复是否只是输入更合理，还是确实提高搜索效率 |
| 按完整 campaign 重复比较 | 预先固定一批任务起点和种子；同一框架、同一总体预算下比较候选生成策略；所有预登记运行都进入统计，单个 campaign 按固定停止规则结束 | 报告成功比例、不确定性、成功前总 token/时长、每次失败原因与人/外部 Agent 介入次数；不能只报最优候选 | 整套自改进程序是否可靠、经济，以及对外部协助的依赖 |
| 责任归因与复评边界故障注入 | 分别注入真实框架存储错误、judge 无有效响应、候选证据不足、分数未决、复评身份不匹配；不修改判断门槛 | 基础设施失败不诱发候选修复；候选责任保留真实来源；未决仅使用预定次数；全部样本和成本入账；不匹配证据拒绝合并 | 系统是否会把环境故障变成错误学习信号，或通过复测制造通过 |

## 6. 建议报告采用的表达

避免“形成可靠闭环”“加强反馈”“建立护栏”这类无法检查的总结。写成可复查的变化，例如：

- “原实现让首份报告耗尽 12 条历史额度，较新候选已通过的检查点没有进入生成输入；修复按报告组轮转分配相同额度，真实输入 A/B 验证选择转向后续候选。”
- “对证据缺口优先删去或限定可选断言，避免为了保留细节新增浏览、ledger 或重试；最终是否同时保住分数和成本，仍由完整配对评估判定。”
- “保留原始拒绝报告，在新源码版本上重跑原命令；这证明拒绝记录未被改写，不等于排除多次搜索后的选择偏差。”

建议报告的主判断是：此次最有价值的经验，是自改进系统首先要准确保存任务、失败责任、已通过检查点及证据来源，否则它会反复修错对象。最终验收说明这一具体闭环在当时规则下跑通；独立、可重复的 RSI 能力仍是后续要验证的问题。
