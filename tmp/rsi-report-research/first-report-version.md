# RSI 实践心得：AWorld self-evolve 优化复盘

2026 年 9 月 18 日

这轮 self-evolve 优化完成了一次可核查的技能改进验收，也暴露了持续改进很容易中断的地方：系统会把环境故障当成候选缺陷，把已经通过的检查点丢在历史记录里，再用更多规则修复一个本来需要收缩的问题。后续候选能否变好，很大程度上取决于它是否收到正确的失败信息，是否继承了上一轮已经验证过的改动。

这里把 RSI 理解为递归自我改进：系统改进自己的行为，并进一步改善产生、选择和验证改进的方法。两个任务实际展示的是外部 Coding Agent 协助下的技能自改进过程。self-evolve 负责生成和评估候选，外部 Agent 持续修复框架，用户明确目标并推动续跑。记录没有覆盖模型权重自改，也没有证明系统能自主、连续地提升自己的改进算法。这个范围决定了下文能得出多大的结论。〔1、2〕

用户要求用同一条命令完成 `agent-browser` 优化：

```bash
aworld-cli optimize \
  --target skill:agent-browser \
  --from-trajectory ~/Documents/trajectory1.log \
  --apply verified_only \
  --judge-agent ~/Documents/agent.md \
  --judge-timeout 600 \
  --judge-model-profile gpt-5.5 \
  --replay-timeout 900 \
  --replay-total-timeout 3600
```

最终成功的那一步改动很具体。成功子候选继承 v19 首轮候选的三份 capability、compiler 和 runtime 支持文件，内容逐字相同，只修改了 SKILL 的抽取指导：保留局部快照、计数和读取等操作，要求答案按实际读取的摘要、元数据或章节说明覆盖范围；没有读过全文，就不能声称完整覆盖；未经核实的细节应删去或限定。同时精简旧教程。它把修改放在答案如何使用已取得的信息上，没有在这一轮重新改造运行支持层。分数提升仍是整包的测量结果，不能据此分摊到某一句规则。〔3〕

通过结果仍有边界。held-out 的证据门禁采用与基线比较的规则，保留一条 `support_incomplete`，`evidence_incomplete` 仍为 `true`；通过表示没有新增或恶化该缺口。报告确认两组回归用例与主选择集不重叠，各套件重新执行；回归和主评估沿用同一实现，`implementation_independent=false`。这些字段不代表两个套件彼此统计独立。此外，报告中的另一套 artifact 因果测量仍处于 `shadow`，`effect_estimate=null`、`promotion_eligible=false`，原因是主效应尚不可用。正式质量门禁、这套影子测量和发布状态是不同口径，不能用其中一项替代其余两项。〔3、4〕

早期排查反复遇到的问题，是确认一次失败究竟该让谁来修。基线筛选已经成功、候选单边超时，框架却因没有识别旧版 `timeoutexpired` 格式，把它送进 framework handoff。修复统一了超时事件的解释，候选随后能够继续进入完整回放。另一次问题发生在 judge：前两次评审正常，后续请求却变成 `messages: []`。排查发现，独立的评审提示走了有状态 Agent runner，嵌套异步任务读写了不同的 memory context。修复改为每次显式构造新的 system/user 消息，直接调用配置的模型。增加候选轮数无法解决这两类错误。〔5〕

预算和断点也有自己的身份问题。增加续跑轮次时，隐式 token 总额没有同步覆盖新增工作；另一次运行把当前 run 的 `1/1` 当作额度用尽，此时 campaign 实际只使用了 `11/12` 个候选。修复先计算累计额度，再决定是否继续，并按候选指纹和未完成用例恢复检查点，避免重复计费。后来又限制已经完成新鲜复评并被否定的旧候选反复复活。持续搜索需要分清“还有工作没测完”和“这个候选已经测过且失败”，否则更多轮次只会增加重复支出。〔1、5、6〕

回放环境也会误导候选。早期 browser runtime 对 `/html`、`/pdf` 等不同路径返回同一份内容和 HTTP 200，候选继续检索，却拿不到新的信息。工作记录记载，一个候选在第 33 次工具调用触碰 32 次上限，尚未完成答案综合。当时一轮修复把回放绑定到真实记录的响应和任务 URL，让未记录路径明确失败，同时调整筛选与权威回放的工具额度。这个案例提醒我，先要让环境如实表达它提供了什么，才能判断候选是否缺少搜索或收敛能力。单纯要求它“再核查一次”，可能只会增加无效调用。〔5〕

这条路径限制并没有成为最终包完整保持的性质。本次检查最终隔离包的 HTTP handler，发现它在正常构造响应时，仍对所有非健康检查路径返回记录内容和 HTTP 200。因此，当前验收对真实网页路径差异的覆盖有限，后续需要专门验证错误 URL 和无新内容时的行为。早期修过某个问题，不能替代对最终候选的检查。〔3〕

这些调整也改变了实验条件。早期 held-out 只评价候选，把基线已有的证据缺陷也当作候选必须消除的问题；后来改成同一数据分组上的基线、候选配对评价，拒绝新增或恶化的约束。工具预算也先后调整，最终形成筛选 12 次、权威回放 48 次的分层额度。因此，命令行参数相同不能推出全过程评估规则相同。最终结果应解释为修复后的 v19 规则下通过验收；早期拒绝和晚期成功之间，既有候选变化，也有评估协议及运行条件变化。〔5〕

进入能完成评审的阶段后，修复方向开始成为主要问题。第一任务记载，曾有候选同时通过分数、成本和延迟，只剩证据问题；修复却没有保住这些已经通过的条件。另一轮把两段改进扩成 46 行全局规则，还有一轮从 38 行扩到 58 行，并增加了面向用户的 artifact-reference 输出要求。每项要求单独看都有理由，叠加后却要求 Agent 在更多任务中做额外查证、记账和重试。〔1〕

后续实现把 judge 后的修复限制得更具体：证据不足时，优先删去或限定缺乏来源支持的可选断言，复用已有证据；回归、成本等修复应收缩作用范围，新增 token 不得超过父候选。框架原先还会在校验之后自动追加“全局完成不变量”，重新扩大候选；后续把这类静默改写转为可反馈的校验失败。这里有一个实用的取舍：任务必需的信息仍要获取，可选细节不值得附带一套全局查证流程。修复必须指明要保留哪些已经验证的行为，不能只要求“解决这个失败”。〔1、6〕

比提示词膨胀更隐蔽的是反馈丢失。后期修复发现，评估链没有完整保留实际执行的任务问题；评审解释在重复评价与压缩过程中消失；validation 失败有时被重建为 held-out 失败。独立回归也出现过两组套件已经产生具体分数和问题，生成器却仍收到主评估的旧反馈。生成器有能力改代码，也无法凭一个脱离对象的“证据不足”准确决定改哪里。〔6〕

这些修复保留了任务输入、实际失败的数据分组以及各回归套件的身份，把有限数量的原始 judge 意见送进既有反馈预算。编译错误同样要保留具体原因：一次 `_write_trace` 的 `TypeError`、一次重复 service ID，如果在层层包装后只剩“启动失败”，下一轮就容易重写已经有效的 runtime。任务输入的恢复也有明确边界，只恢复问题和必要的先前对话，不把参考答案或工具结果混作问题输入。对 RSI 而言，失败反馈需要保留足够的来源和责任信息，压缩不能只剩结论标签。〔6〕

跨轮继承还涉及合法性。有一轮父候选获得了按内容指纹绑定的章节修改授权，子候选继承其内容时，反馈序列化丢失了 `structural_edit_intent`。同样的文本到了下一轮，就成了“未经授权删除代码块”。修复把修改意图与候选内容一起持久化、恢复，仍然限制允许修改的文件范围。只保存一份“最新 SKILL.md”，不足以让下一轮合法地继续已有工作；已经完成的验证及其绑定对象也要保留下来。〔5〕

v18 的历史窗口问题把这个教训表现得很清楚。旧逻辑优先选择带 `repair_focus` 的祖先报告，第一份报告提供了 13 条反馈，加载器总额度却只有 12 条，后续候选已通过的检查点因此进不了生成输入。修复保留 12 条上限，按报告组轮转分配，调整候选排序以反映实际验证进展。用相同历史文件做 A/B，旧代码的 12 条全部来自 cycle 001，修复后能够包含 cycle 003、005 的记录，修复对象随之改变；18 份原生文件的哈希保持一致。〔6、7〕

v19 的实际模型输入随后确认，第二轮接收了第一轮的评分失败，保留已通过的 held-out 观察与回放支持文件，没有退回 v18 的旧候选。这证明历史传递机制在该现场按预期工作。第二轮成功与这种改进相符，但仍不能把最终 +2.8 分全部归因于历史窗口修复；要回答这个因果问题，还需要相同起点和预算下的消融对照。〔3、7〕

统计未决也需要单独处理。v17 有一组独立回归的均值提高了 0.7 分，区间仍较宽，完整验收停在这里。后续为每个回归套件补充最多一次有界复评，固定候选、数据与评估计划，合并全部相容样本，身份不匹配或评审异常时继续拒绝，并把额外消耗计入预算。v19 最终两组回归首轮就通过，并没有使用这次补充复评，不能把成功解释为挑选到了更高的一次分数。〔4、6〕

有界复评解决的是单个候选的测量程序。整个研发过程仍然经历了多轮候选和框架修改，直到出现成功；胜出轮的区间不能代表全部搜索尝试的长期收益。用于修复的回归反馈也已经参与了后续候选生成，最终确认需要另选此前未进入反馈的新任务。再评估这套程序时，我会把每个预先登记的 campaign 都计入结果，保留失败、停止原因和总成本，避免只比较最好的一轮。

长时间运行带来了另一组实际约束：服务进程积累、休眠打断请求、磁盘写满以及清理耗时。后期把真实存储耗尽归到基础设施，补充进程生命周期处理和防休眠保护。资源管理同时影响可复盘性：关联清理任务删除了大量不活跃 campaign，部分早期原始报告已无法复读。当前 Git 提交、工作记录和若干 A/B 校验文件还在，但它们不能补出已经删除的全部现场。早期数字按历史记录引用，本次只做材料核查。〔5、6、8〕

把这些问题放在一起，可以理解为什么任务中几次判断“框架基本稳定”之后，又出现新的框架缺陷。完成回放之后才会走到 judge、独立回归和隔离应用，后面的路径可能此前根本没有运行过。数千项测试能验证许多约定，也不能代替整条真实执行链。更准确的进度记录应指出已经通过哪一阶段、剩余失败属于什么对象，而不是给整个框架一个笼统的稳定性结论。

我会保留这次开发中一个有效的习惯：让当前运行先形成完整报告，在隔离环境中修改框架，再用历史输入 A/B 和相关测试确认具体机制，最后以新的源码版本重跑验收。原始拒绝报告不随修复改写，新的通过也有明确版本。外部 Coding Agent 做的这些工作应单独记账；它们解释了 self-evolve 为什么逐步可用，却不能直接算成 self-evolve 自主改进了自己的优化算法。

下一轮如果要检验更强的 RSI 能力，我会安排以下实验。它们是建议，本次复盘没有执行。

1. 冻结 v19 框架、基线包和最终候选，在未进入任何修复反馈的新任务上配对复验。事先固定任务数、评审重复次数及停止规则，按独立任务处理不确定性；同时声明允许继承哪些基线证据缺陷。通过判据应同时覆盖质量与执行代价，影子测量缺少主效应的问题也要单独补齐。
2. 对历史反馈和收缩修复做等预算消融。使用相同历史快照与候选起点，比较原策略和修复策略的完整 campaign 通过率、总 token、耗时以及外部介入次数。先验证反馈传递正确，再判断它是否提高了搜索效率。
3. 区分候选收益与框架收益。对可兼容的旧、新框架分别运行基线和最终候选；不兼容组合明确记为不可测。用同一框架中的配对差值估计候选收益，避免把协议修正带来的可运行性全部记到技能头上。
4. 验证连续继承。让通过验收的候选成为下一代基线，在固定总预算下完成多个预定代次，再用独立任务复验。只有同时记录累计收益、退化和所需外部协助，才能判断这套程序是否具备持续改进能力。
