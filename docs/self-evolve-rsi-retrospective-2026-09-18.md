# 做 RSI 的一点体会（二）：让改进可验证、可恢复、可累积

围绕同一个 Skill 做了多轮 self-evolve 后，我最大的体会是：RSI 没有成功，不一定是模型不会改，也可能是系统没有回答好三个问题：失败属于谁？留下了什么有效证据？下一轮是否仍在修复同一个问题？

`rejected` 只代表“目前不能证明成功”，不等于“候选已被证明无效”。只有 baseline 有效、candidate 真实执行并形成 paired evidence，失败才有条件归给候选。控制超时、环境漂移和 candidate 未执行，应进入 measurement 或 framework 分支。

## 01 任务表现与改进方法是两张成绩单

self-evolve 同时优化任务策略和改进器。候选分高，不代表搜索方法更好；没产生最高分候选的策略，也可能因减少重跑而更高效。因此要分别记录任务收益和完整搜索成本。

## 02 先有可比较证据，再做失败归因

一轮实验设置了 1800 秒总时限，只完成 5/11 个 baseline，candidate 一次都没执行，却消耗了 3/3 个 authoritative 名额。这不是候选失败，而是实验没有形成对照。

另一次结果是 `88.13 → 88.13`，置信区间跨零，而且三次评估中两次 evidence 不完整。拒绝晋级是对的，但下一步应该修 tie-break 调度和证据链，而不是放宽 success gate。

## 03 反馈必须是可执行反例

曾经有 5 个 requirement 生成 5 个 fixture，却只有 4 个唯一路径。只反馈 `fixtures contain duplicates`，模型可能不断调整哈希和后缀；如果反馈明确为 `compile_result.fixtures` 必须满足 `unique(path)`，并标出责任文件，修复才可能收敛。

Repair Contract 应包含失败对象、不变量、期望值、责任组件和已通过条件。同一根因只形成一个 repair frontier，不要把派生现象拆成多个问题。

## 04 续跑应该恢复实验，而不只是候选

Cycle 2 已完成 7/11 个 case，Cycle 3 却重新显示 11 个全部 pending。候选恢复了，replay checkpoint 没恢复，所谓续跑就变成了重跑。

跨 cycle 应保存候选指纹、评价版本、已完成 pair、无效 control、Repair Contract 和剩余预算。比较条件发生变化时，应建立带 lineage 的新实验。

一次成功候选继承了父代 3 份支持文件，主评分从 86.67 提升到 89.47。这个结果说明，已经验证的实现被保留下来后，搜索才能继续处理剩余问题。

## 05 越接近可用解，修复范围越要小

在较强基线上增加一条全局规则，可能同时改变检索成本、停止条件和回答结构。文本短不代表行为影响小。修复应说明何时触发、改变哪个动作，并验证未涉及任务仍保持原行为；只有确认缺少关键能力时，才值得扩大搜索范围。

## 06 测试通过不等于验证闭环可信

评估器可以改，但任务、测量方法、接受政策和资源条件必须分别记录，否则新旧结果无法比较。实践中多次出现 1800 多项测试通过，下一次真实运行仍暴露跨 cycle 缺口。

回归测试只能证明局部逻辑没有退化，不能替代冷启动、中断续跑和真实进程级验证。“测试通过”和“闭环可信”是两类证据。

## 07 预算应该购买信息，而不是购买尝试次数

三个候选直接进入 11-case 全量 replay，仅 authoritative 阶段就耗时约 8.7 小时，最终只有 7 个 comparable pair、3 个 strict pair。候选确实有问题，但结论本可以更早得到。

多 case 应按 `case 1 baseline → candidate → 落盘 pair` 渐进执行。共同超时应记为预算右删失；candidate 没执行，不应消耗 authoritative 名额；已有证据足够判定，或数学上已经不可能过门时，应立即停止。

我现在更愿意用这条标准衡量 RSI 是否取得进展：

> 进展不是又生成了几个候选、改了多少代码，而是关闭了一个可验证反例，保留了已有有效证据，并把同一个实验推进到更深的可信阶段。

可靠的 self-evolve 系统，首先应该是一个可恢复、可归因、成本有界的实验系统。在这个基础上，模型的“自我进化”才有真实含义。
