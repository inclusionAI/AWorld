# 做 RSI 的一点体会（三）：进化要以完整回归证据为支撑

近期我们针对 SpreadsheetBench 进行一组RSI的实验，实验构建了“初始评测：收集原始trajectory->Skill进化:生成Skill Draft->回归验证：Source Skill与Draft Skill同条件回放验证”的self-evolve闭环链路，借助对Benchmark中的 400 个商业表格任务进行了全量回放，覆盖多 Sheet 数据处理、财务建模、问题修复和可视化，实验结果Source与Draft二条验证路径都通过质量门禁，从通过率来看最终Draft 比 Source 高 1.6 个百分点，结论采用将验收策略转入人工审核，由其判断是否允许此类回归并明确回滚条件，从而提升进化的实际价值。

在实验质量控制阶段我们采用同条件配对回放：Source 与 Draft 在相同输入、模型、预算和评测协议下独立生成并评分，再按 Case 配对。冻结样本、推理条件和评价口径后，Skill 版本是主要受控变量；既能测量整体增益，也能定位被平均分掩盖的单 Case 回归。

验证还采用能力非对称分工：执行模型完成任务，能力更强的独立 Judge 判定质量，并在 Source、Draft 和两条验证路径之间保持不变。结果由更高能力的外部角色审查，固定 Judge 则保证差值仍主要来自 Skill 版本。两条路径在同一 Judge 下都取得提升，也降低了收益只依赖某一种执行方式的可能性。

全量运行结果为：

- 两侧都完成 400 / 400 个 Case 创建；
- 两侧都完成 400 / 400 个候选生成；
- 两侧各完成 800 / 800 次机器评测；
- 合计完成 800 次 Case 创建、800 次候选生成和 1600 次机器评测。

两条验证路径分别从 89.50% 提升到 90.25%、从 86.75% 提升到 89.50%，对应 +0.75pp 和 +2.75pp，汇总提升为 +1.6pp。400 个 Case 均属于未向修改角色暴露的 holdout；按 Case 与验证路径展开后，记录到 36 个修复、22 个回归，0 个证据不完整项。

全部任务正常结束，比较覆盖完整批次，而非少量抽样。1.6pp 的证据范围限于这 400 个任务和固定协议；Case 级结果则说明，整体净提升可以同时包含修复与退化。Promotion 因此需要同时考虑总体收益、回归位置和回滚成本，不能只看平均分是否上涨。从实验结量与过程中收获了以下经验总结：

## 模型修改 Skill，只占闭环的一小部分

此前的多轮运行显示，主要故障集中在输入解析、样本选择、执行约束、证据归属和故障恢复。有些任务没有进入 mutation，有些修改后的 Skill 没有真实重放，还有些运行在非终态退出后重复消耗重试预算。此时即使生成了一份看起来合理的 Draft，也没有证据支持采纳。

因此，系统把模型与确定性控制器分开。mutator 根据失败轨迹提出可证伪假设，executor 用候选 Skill 完成任务，evaluator 独立评分；控制器负责状态、哈希、候选选择、停止和 promotion。模型不能选择 champion，也不能覆盖门禁。

三类 Agent 使用独立上下文。mutator 只能看到脱敏后的失败模式，看不到答案和 holdout；executor 看不到分数与修改假设；evaluator 可以读取答案，但不知道系统期望哪个候选胜出。这样的隔离减少了候选针对评测器取巧的空间。

更强的 Judge 仍不等同于标准答案。两条路径共用同一 Judge，可能共享评测偏差；如果修改角色直接看到完整评分依据，还可能逐渐适配评测器。因此，Judge 输出只是证据的一层，需要与确定性校验、受保护回归项和必要的人工抽查组合使用。修改角色只能获得脱敏后的失败模式，不能接触 holdout 答案。

每个候选只验证一个修改假设。系统先在目标 Case 和少量回归锚点上筛选，再让排名靠前的候选进入完整回归。被列入保护集的稳定通过项一旦回归，就不能晋级；其余回归则按重要性和容忍阈值处理。中间 champion 的选择与最终 promotion 分开，局部进步不会自动获得发布资格。

## 运行环境的稳定性决定实验能否成立

多轮运行后，我把运行环境的稳定性视为 RSI 的基础条件。稳定包括条件不漂移、状态可恢复和证据可追溯。

控制器在任务开始前冻结 Case 范围和评测协议。监督进程根据 heartbeat、终态文件和 checkpoint 恢复长任务，避免重启后重复消耗预算。

生成与评测采用流式流水线。一个 Case 生成成功后立即进入评测，两个阶段独立并发，可以更早发现配置错误并减少任务堆积。

进化阶段优先复用已有失败证据。材料足够时直接诊断或补评，缺少有效产物时才重新生成；promotion 前再完成固定范围的正式回放。

大数据集还需要内外两层循环。内循环在失败优先、覆盖多样性的有限 Case 上搜索，候选达到条件后再进入完整 population replay。此次 400 Case 回放承担的是最终验证，而不是让每个候选在每一轮都跑完整数据集。

Draft、生成文件、轨迹和评测结果必须绑定来源。自动应用前还要复核 Source 指纹、保存备份，并在应用后验证真实加载结果；任一步失败都执行回滚。

跨 cycle 的 Campaign 固定 Source、验证协议、累计预算和 lineage。只有新的修复证据或可重试的环境故障才能继续，失败边界没有变化时停止。这些机制让上一轮证据能够安全进入下一轮。

控制器读取结构化阶段、失败类别和产物来源，不依赖外层 Agent 反复阅读大日志猜测进度。通过校验的产物继续复用，Skill、评测和环境问题可以分开处理。

## 质量门禁需要覆盖局部回归

实现层可以把发布策略分为只保存候选、验证后保留和验证后自动应用。人工审核只是策略选项，不是 Self-Evolve 的必经步骤。

自动升级还需要把 Case 重要性、最大允许回归、证据完整性和回滚条件写进门禁。Source、Draft、评测记录和回滚路径完整保留后，系统可以自动应用、拒绝或继续验证，每种决定都能审计和撤销。

这次运行尚未记录最终版本决策，定向人工对照也未完成。它没有证明人必须逐项审批，反而暴露了一个更具体的问题：当整体收益与局部回归同时出现时，系统采用什么风险偏好。规则尚未编码，就交由人判断；规则足够明确，则可以自动执行并保留人工否决权。

## Self-Evolve 的产物是可执行的升级决策

这次实验产出了一个更高分的 Draft，也留下了局部回归证据。系统应把二者转换成可执行决策，明确自动采纳、拒绝或继续验证的条件。在实验中我们采用了以下五个条件来判断一次 Skill 进化是否成立：

1. Draft 来自明确的失败证据和修改假设；
2. Source 与 Draft 在同一条件下完成真实回放；
3. 整体收益和局部回归都被记录；
4. 接受策略能自动应用、拒绝或继续验证，并支持回滚；
5. Judge 与执行角色相互隔离，并在 Source 与 Draft 之间保持模型和评分协议不变。

在这次实验验证过程中满足了第 1、2、3、5 项，但在第 4 项上当前策略是把局部回归交给人工审核，经过人工补齐业务容忍规则后，同一分支也可以自动应用。

从本次实验最终执行情况来看，RSI 的进展不应只看分数上涨。系统是否保留证据、识别退化，并执行可撤销的升级决策，同样决定这次进化能否进入下一轮。
